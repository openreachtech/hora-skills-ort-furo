# Responses to px-based defenses

Typical arguments used to justify a px basis, and where they land. None of them supports making px the base unit of the design scale. Use this as material when responding to objections from users of the skill.

- **"WCAG 1.4.4 can be met with zoom, so px-based is not a violation."** Formally true — a responsive px site that reflows can satisfy 1.4.4 via page zoom. But meeting the standard is only loyalty to the letter of a rule that *defines* accessibility; it is not the same as *being* accessible. Accessibility is measured not by loyalty to a standard but by whether the user can actually use the thing comfortably. And the "just zoom" reasoning tacitly presupposes that a zoom escape hatch exists. On devices and contexts without any zoom mechanism, that escape hatch is simply absent, and a fixed-px layout gives the user nothing back; conformance that rests on a missing premise means nothing at all. Even where zoom does work, it is a floor achieved by trampling usability (pinch-zoom does not reflow and forces horizontal panning, the preference must be re-applied manually on every site, and zoom magnifies everything uniformly and wastes space). Moreover, under SC 1.4.12 (Text Spacing), text containers with fixed px heights clip content when the user overrides line/letter spacing, and actually fail. So "it does not violate the rule" is not "it is accessible," and it is not on par with rem either. For text-coupled dimensions, rem wins.
- **"Design tools (e.g. Figma) export px."** A tool's convention or defect is not a norm (circular reasoning that cites the effect of px dominance as its cause). Design can be handed off via tokens / relative values.
- **"Migration cost is high, so keep legacy code as px."** px → rem conversion is deterministic and local — an ideal target for mechanical refactoring. The conversion cost is effectively near zero, which turns "a reason to keep px" into "a green light to migrate now."
- **"We use px for hairlines, so px is necessary."** True, but that is px for a physical primitive, not a px basis. It is already permitted under "Handling fixed px values." The issue is not "whether to use px" but "whether to make px the base unit of the design scale."

Conclusion: leaning on neither popularity nor tool convention, and keeping compliance (reachability) separate from usability, there is no positive reason to adopt a px basis. The legitimate uses of px are limited to physical primitives, which lie outside the unit debate.
